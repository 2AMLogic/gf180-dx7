# Decision record: adopt numeric profile v1 (msfa-era integer semantics, Mark I faithful)

- **DR number:** 0003
- **Status:** Proposed (owner sign-off requested on the adoption strategy; all
  defaults otherwise accepted per D00 section 0)
- **Date:** 2026-09-20
- **Deciders:** loom-builder (N01); owner sign-off outstanding on NUM-001 and
  the NUM-011 frame reading
- **Related issues:** #15 (N01), epic #2; depends on #11 (R04), #12 (R05),
  #5 (D01)

## Context

Issue #15 requires one frozen arithmetic/scheduling profile with per-decision
error and cost estimates, and asks whether the pinned Dexed engine's
**existing integer arithmetic** can be adopted as our fixed-model contract so
that model-vs-reference budgets collapse and battle-tested numeric decisions
are reused.

Reading the pinned tree (Dexed `b6cf2e9`, R01) confirms the load-bearing
premise and **corrects the conclusion**:

- The pinned reference engine is Mark I
  (`Source/PluginProcessor.cpp:102,675-686`), and **EngineMkI is an integer
  engine**: 10-bit log-sine and 10-bit sin-exp 16-bit tables generated at init
  by float formulas, 14-bit log-domain envelope gain, int32 accumulation
  (`Source/EngineMkI.cpp:51-150`). No float touches its per-sample path.
- The msfa core (the *Modern* engine, not the pinned oracle) is also integer
  (`Source/msfa/fm_op_kernel.cc:62-64`, `sin.h`, `exp2.h`) — so "the reference
  is already integer" is true of both engines.
- Therefore "adopt msfa semantics ⇒ model-vs-reference budget ≈ 0" **fails as
  stated**: msfa's tables and gain composition differ from Mark I's. What
  survives is stronger: the frozen model can mirror the pinned oracle
  **exactly, integer for integer**, adopting msfa-era *organization* (64-sample
  blocks, per-frame envelope stepping, 32-bit phase, 2-element feedback
  history, `>>4/clip/>>9` output) and Mark I's multiply-free operator core.

Full decision text, per-decision alternatives with error and cost estimates,
the schedule resolution, and the storage analysis live in
[`docs/DECISIONS-NUMERIC-v1.md`](../DECISIONS-NUMERIC-v1.md) with machine
companion [`spec/numeric-profile-v1.json`](../../spec/numeric-profile-v1.json)
(validated by `tests/test_numeric_profile.py` and
`tools/check_numeric_profile.py`).

## Decision

1. Adopt `gf180-dx7-integer-v1` (profile v1) as the frozen arithmetic contract
   for every N02+ integer model and downstream RTL spec: the decisions
   NUM-001…NUM-012 of `docs/DECISIONS-NUMERIC-v1.md`, frozen as of 2026-09-20.
2. **Adoption strategy (NUM-001, the sign-off item):** numeric semantics are
   adopted as *facts*; tables are regenerated by this repository's own
   generator and byte-pinned (provisional float64 regenerations and their
   determinism margins are committed and test-enforced today; N02 requalifies
   against the oracle's runtime tables). **Zero GPL bytes are copied** —
   `Source/EngineMkI.cpp` remains external-oracle-only
   (`docs/REUSE-RULINGS.md: dexed-enginemki`); msfa files remain
   reference-pins adoptable only through DR-0002 governance.
3. **Schedule resolution (issue #15's headline tension):** 96 op-evals/sample
   = 6,144 op-evals/frame = 4.608 M/s. At 12.288 MHz the frame holds 16,384
   clocks ⇒ the op-loop floor is 37.5% (2.67 clk/op-eval all-in — no margin);
   at 24.576 MHz it is 18.75% (5.33 clk/op-eval — comfortable). Design point:
   **24.576 MHz**, with 12.288 MHz as fallback only if the shared operator core
   measures ≤2 clk/eval; ss-corner closure at 24.576 MHz is unproven (D01 §2)
   and must be measured by H01/H10 before any timing claim.
4. **Storage finding:** the exact 16-note state is 32,416 bits (derived from
   the pinned structs); all-register ≈ 3.83 mm² at the family-measured
   118 µm²/bit anchor — 2.3× a quarter-slot core — so a register/SRAM hybrid
   is structurally required; H02 decides the split against these anchors.
5. **DEC-021 numbers (delegated to N01):** silence floor = the exact integer
   predicate "all six operator envelopes in final release at the 16<<16 clamp
   floor", held 64 consecutive frames (85.33 ms), reclaimed output-neutrally
   at the next frame boundary (NUM-012).
6. **DEC-014 alignment (flagged):** events commit at 64-sample frame
   boundaries — exactly the pinned oracle's policy — with DEC-014's queue,
   backpressure, and never-silent-drop rules unchanged; the record reads
   DEC-014's "frame" as the 64-sample core frame (owner may veto; fallback is
   a per-sample event shifter in N02).

## Rejected alternative

A **fresh float FM model** (or an msfa/Modern-semantics model): larger
model-vs-reference error budgets (float rounding or structurally different
tables/gain composition against the pinned oracle), plus more area — a
≥24×24 multiplier (~0.075–0.081 mm² family-measured anchor, derived) and
~0.28 mm² of 24-bit interpolated tables vs ~0.07 mm² of Mark I's two 16-bit
tables and no multiplier. Plan §2 ("How to choose arithmetic?") and §4
(log-domain tables; "study that organization before synthesizing 96
independent multiplier-based oscillators") already pointed this way.

## Consequences

- N02+ implement to the profile, not to upstream Dexed; every deviation from
  the profile needs a new DR and STALE marking of N02–N08, H03/H07/H08,
  R04/R05 budgets, and `spec/numeric-profile-v1.json`.
- The profile is a contract, not a result: `exact_by_construction` entries
  still require N02 byte-level confirmation against the R02 oracle;
  `NO_VERDICT` entries (float-gated amp-mod path) must be measured before any
  model-vs-reference agreement claim.
- No FPGA/synthesis/fit/playback/fidelity/preset-quality claim is made or
  implied by this record (plan §7; AGENTS.md).
- If owner sign-off rejects NUM-001 or the NUM-011 frame reading, N02 must
  re-plan against the recorded alternatives before implementing; the schedule
  and storage findings (items 3–4) stand either way.
